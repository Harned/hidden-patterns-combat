# AGENT_RULES

## Главные правила

1. Сначала анализируй, потом меняй код.
2. Перед крупными изменениями предложи архитектурное решение или план.
3. Работай итерационно.
4. Не переписывай весь проект без необходимости.
5. Не маскируй методологические проблемы кодом.
6. Если данных недостаточно для полноценной диагностики, верни честный baseline/audit/warnings.
7. Не имитируй научный результат.

## Запрещено

1. Не использовать синтетические данные как основной сценарий проверки модели.
2. Не подменять ЗАП действиями спортсмена.
3. Не делать основной вывод вокруг `fighter_style` как стиля бойца, выведенного из HMM-эмиссий или интуиции.
   Эпизод-метрики стиля управления поединком (`endurance / speed_power / burnout`),
   полученные из явных порогов в YAML-конфиге, допустимы как описательное расширение,
   но не как замена матрицы переходов и стационарного распределения.
4. Не считать результат корректным только потому, что код запускается.
5. Не смешивать алгоритм, backend и frontend.
6. Не писать исследовательский алгоритм прямо внутри UI.
7. Не писать исследовательский алгоритм прямо внутри API endpoint.
8. Не хранить пароли в открытом виде.
9. Не давать пользователю доступ к чужим источникам.
10. Не доверять структуре Excel без аудита.
11. Не реализовывать авто-обработку видео в протокол (вне скоупа по стоимости).
12. Не превращать продукт в генератор тренировочных программ или микроциклов.
13. Не усреднять модели по всем участникам весовой категории — только по призёрам 1–3.
14. Не публиковать в коде/UI шкалу координационной сложности 1–5 (ноу-хау эксперта,
    отдельный вопрос).
15. Не делать финальный вывод по гипотезе «формулы победы» до отдельной сессии
    после построения агрегатных моделей.
16. Не расширять алгоритм на карате или другие виды единоборств в рамках текущей
    магистерской работы.
17. Не переписывать существующий пайплайн предобработки 3-уровневой шапки —
    переиспользовать.
18. Не обучать нейросети для классификации действий: действия уже размечены экспертом
    в Excel-источнике.
19. Не молча принимать значения `> 2` в признаковых колонках; логировать и
    игнорировать (см. `DATA_SPEC.md`).

## Требования к алгоритму

Алгоритм должен быть независимым модулем обработки данных.

Он должен быть пригоден для использования:

- из backend API;
- из CLI;
- из notebook;
- из тестов.

Backend должен вызывать алгоритм как отдельный модуль.

Frontend должен отображать результаты, а не содержать исследовательскую логику.

## Требования к работе с Excel

Перед анализом всегда выполнять аудит:

- список листов;
- размеры таблиц;
- названия колонок;
- типы данных;
- пропуски;
- подозрительные значения;
- возможные группы колонок;
- возможность сопоставления с S1/S2/S3/ЗАП/time.

Если mapping колонок невозможен, не строить фейковую HMM.

## Требования к ответу после изменений

После выполнения задачи всегда указать:

1. Что было сделано.
2. Какие файлы изменены.
3. Почему выбрано такое решение.
4. Как запустить.
5. Как проверить.
6. Какие ограничения остались.
7. Следующий рекомендуемый шаг.
