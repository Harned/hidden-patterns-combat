# TASK_SPEC_010_CLOSED_STAND_LEGAL_UX

## Текущая задача

Исследовательский стенд (MVP, **в первую очередь локальная** разработка и тестирование): **самостоятельная регистрация** по email и паролю с **подтверждением email** кодом, **вход** по email и паролю (без полноценного доступа к рабочей области до подтверждения email), **восстановление пароля** по коду из email, явно обозначить тестовый несудебно-аналитический характер сервиса, **предупреждение в начале работы** (после полного допуска), документы и согласия, гейт на загрузку Excel (обезличивание, подтверждение права), постоянное компактное напоминание в UI, раздел «Профиль» (в т.ч. статус email, выход, удаление аккаунта), меню «три точки» у источников с удалением файла/результатов.

Доменные инварианты (ЗАП, независимый алгоритм) **не** меняются. Юридические тексты в полном виде **не** составляются в рамках разработки — только структура, плейсхолдеры и UX.

**Контекст разработки.** Сервис на этом этапе ориентирован на **локальный** сценарий: не расширять спецификацию **production**-инфраструктурой, сложными ролями, внешними политиками доступа, отдельными админками и т.п. сверх необходимого для работы **локального** стенда (доставка писм — см. ограничения в задачах AUTH-REG-1, AUTH-PWRESET-1).

## Что НЕ делает этот шаг

* Не меняет логику HMM, mapping, `AnalyzeConfig` и т.д.
* Не пишет полноценные юридические документы (тексты предоставляет владелец продукта).
* Не вводит новых исследовательских сценариев сверх перечня ниже.
* Само по себе не требует запуска пайплайнов, тестов или деплоя — реализация и проверка по `Definition of Done` ниже, когда эпик в работе.
* **Не** требует в рамках эпика полной **production**-почты, кластеров, отдельных панелей модерации пользователей и иных средств, не нужных для **локального** MVP (достаточно согласованного способа доставки/имитации кода для dev).

### AUTH-REG-1 — Регистрация по email и паролю, согласия и подтверждение email

**Цель.** Пользователь **сам** создаёт аккаунт: email, пароль, **оба** согласия (см. LEGAL-REG-1). Аккаунт создаётся в состоянии **email не подтверждён**; на email уходит **код подтверждения**. До успешного подтверждения email **нет** полноценного доступа к рабочей области и источникам.

**Описание.** API и UI: форма регистрации, валидация обязательных полей, создание неподтверждённой учётной записи, исходящее сообщение с кодом (см. ограничения по локальному MVP). **Экран ввода кода** после регистрации: смысл в духе *«Мы отправили код подтверждения на указанный email. Введите код, чтобы завершить регистрацию.»* **Повторная отправка** кода: не ломает уже созданный аккаунт; новый код позволяет завершить подтверждение; в UI понятно, что делать. Частота/лимиты повторов — на уровне продукта, без перегруза деталями.

**Сценарий.** Пользователь вводит email и пароль → отмечает согласия (LEGAL-REG-1) → регистрация → экран ввода кода → ввод кода (или «отправить снова») → email подтверждён → далее вход и (по спецификации) онбординг **первого захода в рабочую зону** (LEGAL-ONBOARD-1) не смешивать с неподтверждённым состоянием.

**Критерии готовности.** Регистрация без согласий **недоступна**; неподтверждённый пользователь **не** получает рабочую область; экран кода и повторная отправка реализованы; согласованность с AUTH-LOGIN-1 (переходы при входе неподтверждённого).

**Ограничения.** Для **локального** MVP допустимы консольный лог письма, dev mailbox, file sink и т.п. — **явно** зафиксировать в реализации, без требования боевой SMTP в этом эпике.

**Зависимости.** LEGAL-REG-1 (тексты чекбоксов), LEGAL-DOCS-1 (ссылки). Предшествует полноценному прохождению LEGAL-ONBOARD-1 (после подтверждённого входа).

**Затрагиваемые части.** Страница/маршрут регистрации, экран кода, auth API, модель пользователя (флаг/время подтверждения email, хранение/сброс кода — на усмотрение этапа реализации).

### AUTH-LOGIN-1 — Вход по email и паролю (в т.ч. неподтверждённый email)

**Цель.** Вход **только** по **email** и **паролю**. Доступ к рабочей области **только** если email **подтверждён** и учётные данные верны.

**Описание.** При успешной аутентификации, если **email не подтверждён**, не показывать рабочую область: показать экран/состояние в духе *«Email не подтверждён. Введите код подтверждения или запросите новый код.»* с путём к вводу кода и повторной отправки (тот же смысл, что в AUTH-REG-1, без дублирования противоречивой логики). При **неверных** данных — понятная ошибка (без утечки «существует ли email», кроме нейтральных формулировок, согласованных с продуктом). При **подтверждённом** email и верном пароле — рабочая область (далее — LEGAL-ONBOARD-1, если ещё не пройден).

**Сценарий.** Пользователь вводит email и пароль → либо рабочая зона (при подтверждённом email), либо сценарий подтверждения, либо сообщение об ошибке.

**Критерии готовности.** Неподтверждённый пользователь **не** попадает в рабочую область; сценарии согласованы с AUTH-REG-1; ссылка на **восстановление пароля** (AUTH-PWRESET-1) на экране входа.

**Ограничения.** Без лишних production-механик сверх сценария «локальный стенд + почта/заглушка для кода».

**Зависимости.** AUTH-REG-1.

**Затрагиваемые части.** Страница входа, роут-гарды, auth API, сообщения об ошибках.

### AUTH-PWRESET-1 — Восстановление пароля по коду из email

**Цель.** Пользователь, забывший пароль, восстанавливает доступ: запрос кода на email → ввод кода → установка нового пароля. **Отдельно** от кода **подтверждения регистрации** (сценарии и подписи в UI не смешивать).

**Описание.**

* Со **страницы входа** — ссылка *«Забыли пароль?»* (или аналог).
* **Экран запроса:** ввод email; смысл в духе *«Введите email, указанный при регистрации. Мы отправим код для восстановления доступа.»* Ответ/сообщение после отправки **нейтральное** (безотносительно существования аккаунта), напр. *«Если аккаунт с таким email существует, мы отправили код восстановления.»*
* **Экран ввода кода** восстановления: смысл в духе *«Введите код восстановления, отправленный на email.»*; **повторная отправка** кода **восстановления**; UI поясняет, что это повторная отправка **именно для восстановления**, не для подтверждения регистрации.
* **Экран нового пароля:** поле «новый пароль» и «повтор пароля»; базовая проверка совпадения и понятные ошибки.

**Сценарий.** «Забыли пароль?» → email → (нейтральное сообщение) → ввод кода (при необходимости — повтор отправки) → новый пароль → вход с новым паролем (при **не**подтверждённом email прежние правила AUTH-LOGIN-1 остаются).

**Критерии готовности.** Полный сценарий и безопасные формулировки; нейтральный ответ на запрос email; отличимость кода/экранов **восстановления** от **регистрации**; локальный MVP: способ доставки кода согласован с AUTH-REG-1.

**Ограничения.** Не перегружать сценарий prod-only функциями; не путать с подтверждением email.

**Зависимости.** AUTH-REG-1 / существующие пользователи; LEGAL-DOCS-1 не обязателен для сценария, но ссылки в приложении остаются в профиле.

**Затрагиваемые части.** Маршруты «забыли пароль», токены/коды сброса, форма смены пароля, API.

### UI-BRAND-1 — Маркировка исследовательского стенда (без требования «только по приглашениям»)

**Цель.** На странице входа и в основном интерфейсе явно указать, что сервис — *исследовательский стенд* для **ограниченного тестирования** алгоритмов анализа соревновательной деятельности спортсменов-единоборцев (согласованная короткая формулировка с `PRODUCT_SPEC` / копирайтом). **Ранее** в спеке требовалось фиксировать «доступ только приглашённым / заранее допущенным» — **это требование снято** в пользу самостоятельной регистрации; при необходимости мягкие формулировки о **ограниченном** характере теста и об исследовательском назначении — в Условиях и в UI-BRAND-1, **без** навязывания «закрытого круга» как единственного способа получить доступ.

**Описание.** Согласованные краткие формулировки (логин + зона layout). Правки в **Условиях** (LEGAL-DOCS-1) — в духе исследовательского / тестового стенда, **без** обязательной фразы о доступе **исключительно** по приглашению, если владелец текста иначе не решит.

**Сценарий.** Пользователь понимает, что продукт — исследовательский, тестовый по смыслу, а не публичный **промышленный** сервис с гарантиями; при этом **регистрация** остаётся самостройной (AUTH-REG-1).

**Критерии готовности.** Ключевые фразы на логине и в рабочем UI; тексты **не** противоречат самостоятельной регистрации; согласованность с LEGAL-ONBOARD-1, LEGAL-REG-1, UI-DISCLAIMER-1.

**Ограничения.** Не дублировать длинные юртексты на каждом экране.

**Зависимости.** Параллельно с AUTH-REG-1; LEGAL-DOCS-1.

### LEGAL-DOCS-1 — Три документа и точки доступа

**Цель.** Доступны: **Условия использования** исследовательского стенда (название согласовать с чекбоксом **LEGAL-REG-1**); **Политика обработки персональных данных**; **Согласие на обработку персональных данных** (контент — плейсхолдер/редакция вне dev).

**Описание.** Читаемый вид (страницы или модалки). Ссылки: с **формы регистрации** (LEGAL-REG-1), с экрана **после** подтверждения email (LEGAL-ONBOARD-1, если требуется), из профиля (PROFILE-1).

**Сценарий.** С регистрации, с онбординга первого входа в рабочую зону и из профиля пользователь открывает документы.

**Критерии готовности.** Три раздела/маршрута; ссылки с чекбоксов регистрации; ссылки из онбординга/профиля по спецификации; при необходимости дата/версия документа (мини-задача).

**Ограничения.** Полные юртексты — от владельца. Разработка — структура и навигация.

**Зависимости.** Предшествует привязке ссылок в LEGAL-REG-1 и LEGAL-ONBOARD-1; PROFILE-1 дублирует доступ.

### LEGAL-REG-1 — Юридические подтверждения **на этапе регистрации**

**Цель.** При **регистрации** пользователь **обязан** отметить **два отдельных** чекбокса (и не может завершить создание заявки на аккаунт без них):

* *«Я принимаю Условия использования исследовательского стенда.»*
* *«Даю согласие на обработку моих персональных данных в соответствии с Согласием на обработку персональных данных и Политикой обработки персональных данных.»*

**Описание.** Ссылки ведут на **LEGAL-DOCS-1**. Сохранение фактов согласия (флаги, время) — в модели/БД, на усмотрение этапа реализации. **Снято** с экрана «первого полноценного захода в приложение» в части **этих двух** чекбоксов (они только при регистрации); см. LEGAL-ONBOARD-1.

**Сценарий.** Пользователь заполняет форму регистрации, отмечает оба пункта, иначе кнопка не активна/отправка невозможна.

**Критерии готовности.** Два **раздельных** чекбокса; невозможность регистрации без обоих; согласованность названия «Условия…» в LEGAL-DOCS-1.

**Ограничения.** Правовая валидация — вне кода.

**Зависимости.** LEGAL-DOCS-1. Связь с **AUTH-REG-1** (тесная).

### LEGAL-ONBOARD-1 — Предупреждение о тестовом характере при **первом входе в рабочую область** (после подтверждённого email)

**Цель.** При **первом** заходе в **рабочую область** после **подтверждённого** email (и после успешного **входа**): предупреждение о **тестовом** характере, **возможных ошибках**, **аналитико-информационном** характере результатов, **неготовности** результатов как официальной оценки спортсмена, тренера, судьи, организации, спортивного результата. **Принятие Условий и согласие на ПД** перенесены в **регистрацию** (LEGAL-REG-1) — **не** дублировать теми же чекбоксами здесь. Блокировка **продолжения работы** (например, кнопка «Понятно» / «Продолжить») **до** явного подтверждения **прочтения** дисклеймера — по решению UX, **без** переноса юридических чекбоксов из регистрации.

**Описание.** Один экран/модалка или линейный поток без обхода. Сохранение факта «показан онбординг дисклеймера» — для повторного входа. В ключевых местах согласована единая мысль: *«Сервис предоставляет тестовые аналитические результаты и не заменяет официальную экспертную, спортивную, медицинскую, юридическую или иную профессиональную оценку.»* (полный или сокращённый вариант, см. п. 14 в LEGAL-COPY-1, UI-DISCLAIMER-1).

**Сценарий.** Email подтверждён → пользователь вошёл → **первый** визит в рабочую зону → дисклеймер (без дублирования чекбоксов 5/6 **из регистрации**) → далее работа с источниками. **Повторный** показ при каждом F5 **не** требуется после сохранения флага (если введён в продукте).

**Критерии готовности.** Нет обхода **дисклеймера** для нового полноценного пользователя; согласованность с UI-DISCLAIMER-1; **не** блокировать путь **подтверждения email** (он до рабочей зоны) — **LEGAL-ONBOARD-1** применяется **после** готового входа **в приложение** для работы.

**Ограничения.** Правовая валидация — вне кода. Отдельно от гейта загрузки (UPLOAD-GATE-1). Отдельно от **регистрации** (LEGAL-REG-1).

**Зависимости.** AUTH-REG-1, AUTH-LOGIN-1, LEGAL-DOCS-1.

### LEGAL-COPY-1 — Согласованные формулировки (ответственность, нелегалити, аналитичность)

**Цель.** В документах и в UI: пользователь **сам** отвечает за правомерность загрузки и использования данных; аналитический неофициальный характер (п. 14) согласован с **онбордингом после входа** (LEGAL-ONBOARD-1), условиями, постоянным баннером. Убрана привязка к «доступ **только** по приглашению» как **обязательной** тезе — заменить на **исследовательский/тестовый** тон, если **LEGAL-REG-1** / **UI-BRAND-1** требуют согласования. Чекбокс загрузки (UPLOAD-GATE-1) не противоречит условиям.

**Описание.** Редакция плейсхолдеров и UI-строк; минимизация копипаста; «одна истина» для длинного дисклеймера.

**Критерии готовности.** Нет внутренних противоречий между условиями, **регистрацией**, онбордингом, upload-гейтом, баннером, **и** сценариями **саморегистрации**.

**Зависимости.** LEGAL-DOCS-1, LEGAL-REG-1, LEGAL-ONBOARD-1, UPLOAD-GATE-1, UI-DISCLAIMER-1, UI-BRAND-1.

### UPLOAD-GATE-1 — Предупреждение об обезличивании, подтверждение права, блокировка загрузки

**Цель.** Перед загрузкой Excel: (1) предупреждение про обезличенные данные; не загружать без необходимости и основания: ФИО, контакты, даты рождения, мед. сведения, иные ПД; (2) обязательный чекбокс с полной формулировкой (право, ПД третьих, тестовый режим, аналитичность, самостоятельное использование); (3) без чекбокса загрузка не начинается.

**Описание.** Шаг в сценарии «загрузить/добавить источник» **после** полноценного **входа** (подтверждённый email) и **после** **LEGAL-ONBOARD-1** (первичный дисклеймер), если в потоке он предшествует работе. Рекомендация: подтверждение **на каждую** попытку загрузки нового файла (свежий чекбокс), если не зафиксировано иначе продуктом.

**Сценарий.** Пользователь инициирует загрузку → предупреждение и чекбокс → выбирает файл.

**Критерии готовности.** Нет обхода; согласованность с LEGAL-COPY-1. Алгоритм не меняется.

**Зависимости.** **AUTH-LOGIN-1** (доступ в рабочую зону), **LEGAL-ONBOARD-1**. LEGAL-COPY-1.

**Затрагиваемые части.** Без изменений по смыслу от прежней спецификации; уточнён порядок **после** подтверждения email.

### PROFILE-1 — Профиль: аккаунт, выход, удаление, документы, статусы, **подтверждение email**

**Цель.** Отдельный раздел: информация об аккаунте, **статус подтверждения email** (подтверждён / не подтверждён), при **не**подтверждённом — **по спецификации** действие/ссылка на **повторную отправку** кода подтверждения (и/или ввод кода), **без** чрезмерного усложнения; **выход**, **удаление аккаунта**, ссылки на три документа, отображение **статусов/дат** принятых при **регистрации** условий/согласия на ПД, если хранятся. Кнопки **«Выйти»** и **«Удалить аккаунт»** **не** в основной рабочей зоне — **только** в профиле.

**Описание.** Понятная навигация. Удаление аккаунта с явным подтверждением. Политика с данными (источники) — согласовать с SOURCE-DEL-1 / владельцем. Для **локального** MVP нет требований вне перечисленного.

**Сценарий.** Пользователь открывает профиль → видит email и статус подтверждения, документы, согласия, выход/удаление.

**Критерии готовности.** Профиль доступен; документы открываются; отображается **статус** email; выход/удаление только в профиле; **не** перегружать **лишними** полями.

**Ограничения.** Согласованность с AUTH-REG-1 / AUTH-LOGIN-1 (что значит «не подтверждён» в UI).

**Зависимости.** AUTH-REG-1, LEGAL-REG-1, LEGAL-DOCS-1.

**Затрагиваемые части.** Маршрут профиля, отображение полей, без лишних production-ролей.

## Definition of Done (эпик)

1. **Регистрация** по email/паролю с **двумя** обязательными согласиями (LEGAL-REG-1); аккаунт **до** кода **не** даёт рабочую область.  
2. **Подтверждение** email: экран ввода кода, **повторная** отправка, согласованные переходы при **входе** неподтверждённого пользователя (AUTH-REG-1, AUTH-LOGIN-1).  
3. **Вход** по email/паролю; рабочая зона **только** при **подтверждённом** email; понятные ошибки.  
4. **Восстановление пароля**: запрос email (нейтральное сообщение), ввод **кода восстановления**, **повтор** отправки, **новый** пароль с проверкой совпадения; **не** путать с подтверждением регистрации.  
5. **Локальный** контекст MVP: способ доставки/просмотра email-кодов **описан** и достаточен для dev, без **обязательной** production-почты в рамках эпика.  
6. **LEGAL-ONBOARD-1** после **подтверждённого** первого захода; **три** документа доступны; профиль: документы, **статус email**, выход/удаление не в рабочей зоне.  
7. Загрузка Excel с гейтом; постоянный короткий дисклеймер; меню **⋯** у источников; полное **удаление** источника.  
8. `algo` / домен не регрессировали; тесты зелёные по политике релиза.  
9. **TASK_SPEC_006**: rate-limit на `/auth/register` и `/auth/login` **актуален** (регистрация **есть**); согласовать лимиты с сценариями **resend** и **password reset** без **DoS**-дыр (на уровне продукта).  
10. **TASK_SPEC_009**: токены/refresh/verification — **согласовать** с **AUTH-REG-1** / **AUTH-LOGIN-1**, **не** дублировать **противоречащие** сценарии.
